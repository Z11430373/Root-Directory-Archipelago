## 1. 北極星與範圍

**這份文件是什麼**：把《根目錄群島》從「15 分鐘試玩版〈第一夜〉」長成「可以玩一整季的完整版」的施工藍圖。只規劃，不開工；劇情以[故事聖經](https://claude.ai/artifact/EFjvSgDXw45rqiBuucmoBv)為準（舊設定一律保留，只增不改）。

**北極星（一句話）**：在瀏覽器裡玩一個真的會壞掉、而且可以「回到昨天再試一次」的伺服器；學會的不是背指令，而是看懂系統為什麼這樣壞。

**三個同時要成立的目標**

- **玩家**：新手能從 `ls` 一路玩到讀懂 `git blame`，沒有死路；老手有隱藏發現、速度與分支玩法可挖。
- **活動**：每個版本都能單獨辦活動，不依賴伺服器（試玩版已驗證這條路）。
- **作品集**：每個里程碑都留下可量化、可展示的東西——事件溯源存檔、雜湊鏈、對照測資、突變測試、伺服器重放反作弊。

**範圍分四層**（越往下越晚、越可砍）

| 層 | 內容 | 依賴 |
| --- | --- | --- |
| 核心 1.0 | 單機離線：Ch0–Ch7 主線（含 Ch3.5 支線）、分支 B0–B7、4 結局＋隱藏結局、本地判題的工單、存檔／匯入匯出 | 試玩版引擎與資料管線 |
| 加分 1.0 | 白帽紅隊學院 7 案、守護夜班 7 夜、多人離線（存檔交換、知識卡合併、合併衝突謎題） | 核心 1.0 |
| 線上 1.x | 帳號與存檔同步、伺服器重放驗證、搶島戰與十二週賽季、OJ 工單接 QDUOJ、管線接力 | 加分 1.0＋後端 |
| 之後 2.x | MUD 地城、偵探懸案、燈塔機房經營、課堂學期（老師面板） | 線上 1.x |

**四條不變原則**

1. **資料先於引擎**：章節、工單、對話、知識卡都是資料檔；試玩版是完整版資料的嚴格子集（ID 不改、存檔 schema 1 共用）。
2. **離線優先，線上是加法**：任何功能必須先有離線版本；線上只增加「驗證、同步、對戰」，不改規則。
3. **每章可獨立發布**：一章＝一個章節包（資料＋對照測資＋驗收清單），做完就能辦一場活動。
4. **沒有測試的內容不算完成**：每章都要過「真 bash 對照」與突變測試（故意弄壞資料，驗證器必須抓得到）。

**這一版刻意不承諾的事**：真實 shell、真實漏洞利用、前端防作弊（只有線上重放能做到）、手機上的完整終端體驗（先求可玩，再求好用）。

## 2. 模式矩陣與玩法支柱

同一份故事、同一份存檔格式，三種連線層級（對應聖經第 9 節）。下表是「哪個玩法在哪一層、哪個版本開放」。

| 玩法 | 單機離線 | 多人離線（存檔交換） | 線上 |
| --- | --- | --- | --- |
| 探索主線 Ch0–Ch7 | 1.0 完整 | 1.0：可交換知識卡、合併衝突謎題 | 1.x：存檔同步、伺服器重放 |
| 解題工單（OJ 風格） | 1.0：本地判題（測資隨章節包） | 1.0：互相出題、交換解法 | 1.x：接 QDUOJ，真正判題與排行 |
| 時間線分支 B0–B7 | 1.0 完整 | 1.0：分支比較、合併 | 1.x：回溯收費與次數限制 |
| 白帽紅隊學院 | 1.0：7 案（靶機純模擬） | 1.0：紅隊／藍隊分工 | 1.x：排行與報告互評 |
| 守護夜班（藍隊） | 1.0：7 夜 | 1.0：輪班 | 1.x：同夜對戰 |
| 搶島戰與十二週賽季 | 不做（只有劇情） | 簡化版：手動回報戰果 | 1.x：完整賽季、四陣營 |
| 管線接力等其餘模式 | 2.x | 2.x | 2.x |

**五根玩法支柱**（每個功能都要能回答「它在強化哪一根」，答不出來就砍）

1. **終端機即介面**：所有行動都是指令；按鈕只是指令的捷徑，不是另一套玩法。
2. **壞掉的是系統，不是玩家**：失敗永遠有可讀的原因（log、錯誤訊息），學的是診斷。
3. **分支即時間機器**：在分支裡亂搞不要緊，只有知識卡能合併回主線（聖經第 1 節）。
4. **每 2–3 分鐘一個小滿足**：沒有任何一段超過 3 分鐘沒有回饋（試玩版已用這個節奏驗證設計）。
5. **沒有死路**：三階提示、`skip`、`hint`；卡住永遠有出口，但不扣掉想自己解的人的樂趣。

**同一章的三種體驗差異**（例：Ch2 權限堡）：單機＝一個人輪流扮演三位值班員；多人離線＝三個人各拿一把鑰匙，交換存檔才能開門；線上＝同一座堡裡即時組隊。故事文字不變，只變「誰能做哪件事」。

## 3. 系統架構

**一句話**：一個「確定性引擎」同時跑在瀏覽器和伺服器上——瀏覽器用它玩，伺服器用它重放驗證。資料、規則、判題、存檔各自獨立。

**六層**

| 層 | 職責 | 試玩版現狀 | 完整版要做的事 |
| --- | --- | --- | --- |
| 資料層 | 章節、工單、對話、知識卡、檔案系統快照的 YAML | 已有（Ch0–Ch1） | 每章一個章節包；編譯成 JSON，帶版本與雜湊 |
| 引擎層 | 虛擬檔案系統、指令語意層、flow 規則引擎、對話執行期 | 由代理建置中 | 改用 TypeScript，與試玩版共用同一份 flow 規格 |
| 存檔層 | 事件溯源 commit 鏈、分支指標、檢查點、完整性分級 | schema 1，代碼 RA1 | schema 2（只加欄位）、快照壓縮、檔案優先 |
| 判題層 | 檢查「這個指令序列／結果」是否符合快題、工單 | 快題 7 題、真 bash 對照 | 工單本地判題；線上接 QDUOJ |
| 前端 | 終端、地圖、值班證、存檔頁 | 單檔 HTML | 地圖、章節選擇、分支視覺化、手機版必備的按鈕列 |
| 後端（1.x） | 重放驗證、帳號、存檔同步、賽季、OJ 橋接 | 無 | 見下方「後端」 |

**確定性是硬規定**：引擎必須是 `(狀態, 輸入, 種子) → 新狀態` 的純函式。引擎內不准直接讀 `Date.now()` 或 `Math.random()`；時間用虛擬時鐘，隨機用存檔裡的種子。這樣伺服器才能「重放同一份 commit 鏈、得到同一個結果」，這也是線上防作弊的唯一基礎。驗收：同一份存檔在瀏覽器、Node 上重放，鏈尾雜湊必須一致。

**語言與工具**

- **引擎：TypeScript＋同一份程式碼跑在瀏覽器與 Node**。試玩版的原生 JS 可直接升級，不重寫。
- **Python 參考模擬器保留**：它是「規格的標準答案」，前端和後端有任何分歧，以它和真 bash 為準。
- **建置**：esbuild 切成「引擎＋章節包」。活動用單檔版（`file://` 可開），正式版用靜態站＋章節包延遲載入＋ Service Worker 離線快取。

**存檔的成長問題**：完整版 commit 鏈會變很長。做法：每章結束寫一個「檢查點」（帶狀態摘要與前一個檢查點的雜湊），舊 commit 可壓縮成檔案，但保留「重放到任一檢查點」的能力。代碼格式 RA1 僅用於試玩版與小存檔；完整版以 `.rasave` 檔為主，超過上限就不提供代碼。

**後端（1.x）的三個服務**

1. **重放驗證**：收到存檔後在伺服器重跑引擎，結果一致才納入排行；「完整／可疑／損毀」再加一級「已重放」（這一級才允許寫「已驗證」）。時間以伺服器收件為準，不信前端的 `r`。
2. **存檔同步與帳號**：只存 commit 鏈與暱稱，不存真名、不存 email 以外的個資；衡突解法沿用「以平行紀錄匯入，不覆蓋」。
3. **OJ 橋接**：工單題目映射到你架的 QDUOJ 題目 ID；玩家在遊戲裡「送出」解法，由 OJ 判題，結果包成實體世界的判題訊息（聖經第 6 節）。離線版則用本地測資，兩邊題目 ID 相同、判題合約相同。

## 4. 內容路線圖（Ch0–Ch7）

章節內容以故事聖經第 3 節為準，這裡只排「先做哪章、每章要交什麼、每章依賴什麼」。碼數與分鐘都是**設計目標，不是量測**（沒有真人試玩過）。

| 章 | 島 | 核心指令與概念 | 分支 → 知識卡 | 交付備註 |
| --- | --- | --- | --- | --- |
| Ch0 值班第一天 | 燈塔島 | `ls` `cd` `cat` `grep -r`；碼片 F1 | B0 → K0 | 試玩版已涵蓋大部分；要補 T0100、鑰匙幣、完整引導 |
| Ch1 日誌港 | 日誌港 | 管線、重導向、`fsck`；第一張 OJ 工單 | B1「封鎖」→ K1 | 試玩版只有 3,315 行日誌，正式版約 120 萬行，需要「可產生」的日誌而非手寫 |
| Ch2 權限堡 | 權限堡 | `ls -l` `chmod` `id` `sudo`；第一次組隊 | B2「改寫」→ K2 | 憲章 Rev 1–5 的伏筆位置要和 Ch0、Ch6 對得上 |
| Ch3 郵局島 | 郵局島 | `grep -l/-A` `find`、mbox 信件；碼片 F4 | B3 → K3 | 信件要用生成器產生大量雜訊，線索手寫 |
| Ch3.5 排程礦坑（支線） | 礦坑 | `crontab` `at`、時間推理 | B3b → K4 | merge／fork 結局需要，所以「可選」不等於「可稍後」 |
| Ch4 網路群礁 | 群礁 | `ping` `traceroute` `ssh`；第一次 PvP、管線接力；碼片 F6 | B4 → K5 | PvP 與接力在離線版用 NPC，線上才是真人 |
| Ch5 記憶體沼澤 | 沼澤 | `ps` `top` `kill` `ln`；Boss「回收波」三階段；碼片 F7 | B5 → K6 | Boss 戰是第一個「狀態機」型關卡，需要額外的引擎功能 |
| Ch6 備份冰原 | 冰原 | `tar` `gzip` `diff`、`git log/blame/bisect`；碼片 F8 | B6 → K7 | 讀 git 歷史需要「仿 git 小引擎」。這是工程量最大的一章 |
| Ch7 根目錄 | `/` | `ls -ltr` + `cat` 拼 root.key、8 空格、遺物收束、結局 | B7 → K8 | 四結局＋隱藏結局，和前面所有分支、遺物連動，實測最繁重 |

**這個順序的理由**：不要一章一章做到完美。先做「垂直切片」——Ch0（補完）→ Ch1 → Ch2，這三章跑完就有「一個完整的上半季」：管線、權限、組隊、分支、OJ 工單五種機制都出現過。Ch3–Ch4 是中段（資料量、多人玩法），Ch5–Ch7 是重引擎的尾段（狀態機、git 引擎、結局）。

**章節包驗收模板**（每章都照抄試玩版的做法）

- 資料驗證器 0 errors；劇透護欄（不提前揭露碼片總數、結局）。
- 真 bash 對照：該章新增指令在章節檔案系統上的行為，與真 bash 對照一致。
- 至少三條走法路徑：黃金路徑、全程 `skip`、分支亂搞路徑，都能跑到章末，沒有死路。
- 突變測試：故意弄壞資料、規則、判題，驗證器必須抓到。
- 時間預算：目標 25–40 分鐘一章（快／中位／慢三種玩家），整條主線約 4–6 小時；第一次真人試玩後重新校正。
- 匯入匯出：上一章的存檔可以匯入下一章；試玩版存檔可匯入 Ch0。

**指令白名單的成長**：試玩版 29 個；每章大約新增 5–10 個，到 Ch7 預計約 70–90 個（估計）。每新增一個指令就要有：行為規格、真 bash 對照案例、不支持選項的回應訊息。不支持的永遠回「不支持」，不准當掉。

## 5. 島嶼占領與經濟層

規則以故事聖經第 7 節為準：每座島 8×8＝64 個區塊、完整度 0–100、快題佔領與修補、慢題（OJ Boss）奉島主、GC 每日 02:00 掃描、每隊每週一次八小時維護窗、十二週賽季與季末 `vote`。以下是「怎麼實作、怎麼防作弊、怎麼調平衡」。

**哪些在哪個層級**

- **單機離線**：不做領地。只有劇情與 NPC 世界的「地圖亮起來」效果，避免「單人假裝有對手」的承諾落空。
- **多人離線**：簡化版。每張存檔帶一份「戰報」，主持人用工具合併成全場地圖（適合社團、教室）；可信度標記為「自行回報」。
- **線上**：伺服器是唯一的真相。所有區塊變更都在伺服器端產生、重放、記帳。

**伺服器權威的戰鬥流程**

1. 玩家向伺服器「領」一張攻擊／修補工單：伺服器發一個**單次使用的 nonce 與種子**，題目參數由種子產生（答案不能從別人那裡抄）。
2. 玩家在瀏覽器解題；快題送出「指令序列＋結果」由伺服器重放判定，慢題送出程式碼給 OJ 判題。
3. 伺服器把結果套用到區塊（完整度、擁有者、稅收），寫進賽季事件日誌，再自動生成《封包海日報》。
4. GC 每日 02:00（以賽季設定的時區為準）跑一個確定性的衰退任務；同一份事件日誌重跑，結果必須相同。

**經濟（鑰匙幣，暫定）**——全部是遊戲內貨幣，不接真錢，也不賣優勢。

| 來源（進） | 去路（出） |
| --- | --- |
| 快題、慢題、工單、題目買到的「修補等級」 | 修補區塊、預約維護窗、三級提示（`man`） |
| 島主稅收（領地越大、維護越貴） | 線上的分支回溯（聖經第 1 節：連線版回溯收費） |
| 季末結算的陣營獎勵 | 改島的登入歡迎詞、改備份策略等「裝飾」 |

**平衡的四條原則**

1. 新隊伍第一週永遠活得下去（種子區塊、前七天維護費為零）。
2. 領地越大衰退越快，門檻是「保持活躍」，不是「一開始就拿到」。
3. 任何讓某隊長期領先、越領先越容易再領先的路，都要有至少一個機制把它拉回（維護成本、回收波、叛變季）。
4. 機制改動先在模擬器上跑。

**平衡模擬器（規劃工具，尚未開發）**：用多代理人模擬 12 週賽季，輸出各隊區塊數、鑰匙幣、存活率。驗收用「有牙的測試」：故意把稅率調到 10 倍、把衰退關掉，模擬器必須對這些壞參數宣告「失衡」。目標不是精確的公平，而是抓到「滾雪球」與「新人殺手」。

**反作弊與濫用**

- 前端結果一律不信，只信伺服器重放；種子＋nonce 防抓答案。
- 每個帳號每日可領的工單數有上限，防大量小號「刷」區塊。
- 暗械達成（比如隨隊友互相交换答案）無法完全妨止，用「同一局的題目參數不同」降低價值。
- 暱稱格式限制與檢舉機制；不收真名。

**採取的預設**：不做真錢、不做抽卡、不做開放聊天室；賽季結束時全部重置，只留「名人堂」與徽章。

## 6. 白帽模式與安全邊界

內容以故事聖經第 4 節（白帽紅隊學院，7 案）與第 5 節（守護夜班，7 夜）為準。這一節只定「這個模式怎麼保持安全、怎麼驗收」。

**基本立場**：白帽模式教的是「理解攻擊面以便防守與修補」，每一案以「報告＋修補」為終點，不是以「拿到 shell」為終點。紅隊第一手、藍隊第一手都有，每案必交報告。

**硬邊界（不可讓步）**

1. **全部是自建的模擬靶機**：不連、不掃、不測玩家自己的真實網路與主機；模擬器不提供任何真實網路的出口。
2. **不提供可用的攻擊程式**：漏洞是「設定錯誤與逻輯錯誤」（便利貼、777 權限、過期備份、輸入框陷阱），不是要玩家寫或貼上真實的利用程式碼。無 payload、無 shellcode、無繞過失效的教學。
3. **不針對真實組織與真實網站**：劇情裡所有資產都是虛構。
4. **白帽守則（Ops Code）每案開場都要簽**：授權範圍、報告義務、不外洩。違反守則的行為在模擬器裡會被標記並扣分。
5. **所有「實作」都是模擬結果**：不執行玩家輸入的程式碼；判題層只檢查「指令序列／狀態結果」。

**審核機制**

- 每案附一張「安全檢查表」：是否出現可直接複製的真實攻擊指令、是否指向真實系統、是否這一案的教學重點是「修」。
- 驗證器強制規則：白帽章節不得包含真實的主機名、公開 IP（文件保留網段除外）、常見真實漏洞編號的利用步驟；突變測試必須抓到故意塞進的危險內容。
- 外部審閱路線：白帽章節發布前，由不同於作者的人（你的老師或社群有資安背景的人）讀一遍，這一步無法由 AI 或自動工具取代。

**年齡與玩家範圍**：預設面向高中以上、有興趣的初學者；白帽模式標明「僅限模擬靶機」，每案結尾都要問「你怎麼修」。

**與主線的關係**：白帽／夜班是**可選**的，不影響主線結局；但完成後會解鎖「紅／藍的視角」跨章彩蛋。

**驗收**：七案、七夜各自有章節包驗收（見第 4 節），外加安全檢查表必須全部勾完，外部審閱留下紀錄。
